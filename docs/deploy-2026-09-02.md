# The first deployment, and what it found

`terraform apply` into account `308857099262`, `eu-west-1`, 2026-09-02.
61 resources created. Torn down the same evening.

Green CI proves the code that was pushed. It does not prove the thing that is
running. Three things were only findable by deploying, and one of them is not
fixable in this repository at all.

## What held

**The privilege boundary, live, from AWS rather than from us.** Each role was
asked for the publish credential and the answer recorded:

| role | may publish | reaches the credential | what AWS said |
|---|---|---|---|
| `merismos-reader` | no | **no** | `AccessDeniedException` |
| `merismos-evaluator` | no | **no** | `AccessDeniedException` |
| `merismos-writer` | yes | yes | granted |

That is `/identity` attempting the read, not reporting a flag.

**A published record is readable by a stranger, and the filing is not.**

    records/probe.md          HTTP 200   the record anyone may read
    orgs/pantry-kypseli.json  HTTP 403   the network's own filing

Both from an unauthenticated request. The bucket policy opens one prefix and
nothing else, which is why the second line is a 403 rather than a leak.

## What broke, and was ours

**A Function URL with `authorization_type = "NONE"` is still not public.** It
also needs a resource policy granting `lambda:InvokeFunctionUrl` to `*`. Every
plan was green, `terraform validate` passed, the apply succeeded, and the first
`curl` came back `403`. Fixed in `infra/main.tf`.

**`/identity` reported the Python class name instead of AWS's answer.** It said
`ClientError`, which is not evidence: a typo in the secret name produces one
too. The AWS error code inside it says `AccessDeniedException`, and that is the
word that means IAM refused. The table above is the fixed version.

**300 seconds was not enough for the reader.** One specialist reading with
Claude Opus 5 takes about 100 seconds and a run wakes four. Raised to 900, the
Lambda maximum, on a measurement rather than a guess.

## What broke and is not ours

**Public Lambda Function URLs are refused in this account.** After the
permission fix the URL still answered `403`, with Lambda's own Function URL
authorization message. Checked and ruled out, in this order: the URL's
`AuthType` really is `NONE`; the resource policy really does allow `*` on
`lambda:InvokeFunctionUrl` with the right condition; there are no service
control policies, no resource control policies and no declarative policies in
the organization, and no policy types are even enabled on the root; and this is
the management account, which SCPs would not bind anyway.

Then the decisive test, because everything above is circumstantial. A throwaway
Lambda was created with nothing but a two line handler, a public Function URL
and the same permission:

    probe url:  https://tx2hwepgtgfoofwnwcr65zlfmq0knxip.lambda-url.eu-west-1.on.aws/
    probe HTTP: 403

**A minimal public Function URL is refused in this account too**, so it is not
this repository's Terraform and not this repository's code. The probe was
deleted immediately.

The consequence is worth stating plainly rather than working around: **the one
endpoint a judge could open with no account does not work in this account, and
no change to `infra/` will make it.** What still works with no account is the
published record in S3, which is the surface the product is actually about. If a
live HTTP endpoint is wanted, it needs either whatever account level restriction
this is lifted, or a different fronting service, and neither is a code change.

## What was not proven

The full deployed run with the live model is a separate record. Nothing here
says anything about reliability: every row above happened once.

## The full deployed run, and the design fault it exposed

`offer-4483` through the deployed reader, **154.2 seconds**, all four
specialists, three of them reading with Claude Opus 5 and the fourth degrading
safely.

    capacity     needs_changes  57.2s   found the empty allergen field vs the manifest
    equity       needs_changes  33.9s   found the whole-lot condition vs the 40% ceiling
    food-safety  needs_changes    -     model unreachable, deterministic answer kept
    premises     needs_changes  54.5s   wine, pork and hazelnut, three members excluded
    critic       eu.amazon.nova-pro-v1:0, two advisories

`food-safety` is the interesting row. Its model call failed and the run did not:
it kept the deterministic answer and left a `model-unreachable` finding saying
so. A half-run did not read as a clean one.

**And the fault.** The read budget was twelve per run, shared across the woken
set. The first specialist took ten. The rest ran with two, then none, and each
spent a model call to report that it had been starved. From the logs, verbatim:

> I have spent my budget. Two reads gave me the decisive facts; the register of
> organisations remains unread, which is itself a finding.

> I have not proposed any allocation, and deliberately named no organisation.

That is the safety property holding exactly as designed: a starved specialist
refused to invent, named what it could not read, and returned `needs_changes`
rather than `ok`. But three model calls to produce three findings that say "I
could not read anything" is a design fault, not a result, and which specialist
gets starved is decided by alphabetical order.

The budget is now **per specialist**, six each. The run total is still bounded
and still reported, as the sum. Two tests pin it, including one asserting that
the last specialist to run starts with as much budget as the first.

None of this was visible offline. One specialist against one corpus cannot show
a pool being spent in order, which is the argument for deploying restated.
